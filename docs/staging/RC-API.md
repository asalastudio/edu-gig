# Release candidate API contract (Task 1)

Local implementation contract, September 8 2026. Deployment, key configuration, migration application and live journey verification are controller-owned. No production authorization is implied.

## Configuration

Convex: `PRIVATE_FILE_KEY` is exactly 64 hexadecimal characters representing a cryptographically random 256-bit AES key; `PRIVATE_FILE_KEY_ID` is its non-secret stable identifier. Both are server-only. Missing/mismatched keys fail closed. Keep the key securely backed up for data recovery; this release does not perform key rotation. Existing staging resource checks and Clerk issuer/allowlist remain mandatory. `NEXT_PUBLIC_APP_URL` must be the exact origin (no trailing slash): staging is `https://k12gig-staging.vercel.app`. Next and browser: `NEXT_PUBLIC_CONVEX_SITE_URL` is the staging deployment's HTTPS `.convex.site` HTTP origin. Never point it at production.

## Upload and download

1. Authenticated `api.privateFiles.requestUpload({ purpose, engagementId?, needId?, fileName, mimeType, size, requestId })` returns `{ ticketId, expiresAt, uploadPath: '/private-files/upload' }`. `purpose` is `agreement | resume | credential | proposal`. Agreement requires an active/in-progress engagement; proposal requires an open/interviewing need. Resume/credential/proposal require the educator role. Resume/credential have no engagement/need ID. IDs are Convex branded IDs. The request ID must be stable for one retry and new for a different selection/input. Tickets expire after 15 minutes.
2. Obtain the signed-in user's Clerk JWT with template `convex`. Call `uploadPrivateFile({ file, ticketId, token, signal? })` from `src/lib/private-upload.ts`, or POST the raw bytes directly to `NEXT_PUBLIC_CONVEX_SITE_URL/private-files/upload` with `Authorization: Bearer <JWT>`, `X-Upload-Ticket: <ticketId>`, and exact registered `Content-Type`. Returns `{ privateFileId }`. Repeating the ticket with identical bytes returns the same receipt; a different body fails. Only the internal HTTP finalizer accepts a storage ID. Browser upload bypasses Vercel's buffered 4.5 MB request cap; limit is 10 MiB, not 4.5 MB.
3. `api.privateFiles.metadata({ privateFileId })` returns `{ privateFileId, fileName, mimeType, size, sha256, downloadUrl }` after current authorization. `downloadUrl` is `/api/private-files/<privateFileId>`; navigate/download using this cookie-authenticated Next route. It forwards a fresh Clerk JWT and streams the authenticated Convex response without buffering the body. Direct HTTP GET `/private-files/download?fileId=<id>` also requires a valid JWT on every request. Unauthorized anonymous/foreign requests fail. All responses are private/no-store with no-sniff and CSP sandbox. Download uses attachment disposition. PDF View uses the same application or direct HTTP URL with `?view=1` (or `&view=1` when a query already exists), authorizes identically on every request and uses inline disposition only for PDF. Other formats remain download-to-view. No plaintext Convex object URL is returned.
4. Proposal-specific download uses `/api/private-files/proposals/<proposalId>` or authenticated Convex `/private-files/download?proposalId=<id>`. This checks the submitting educator or district managing that exact need, including when the attachment originally came from a directory resume.

Formats (controller clarification preserving existing support): agreements PDF/DOCX; resumes and proposal uploads PDF/DOC/DOCX; credentials PDF/PNG/JPEG. MIME, extension, signature, actual/registered length and 10 MiB limit are enforced. Avatars remain on the separate public image path. Files are encrypted AES-GCM with random 96-bit nonce, exact-byte SHA-256, and hash-bound authenticated data. Ciphertext metadata/IDs alone cannot decrypt the contents.

Directory audience: owner plus authenticated district roles may retrieve a currently attached directory resume/credential. Other educators cannot. Old resume files cease directory visibility after replacement but remain accessible to managing districts of proposals that attached them. Private agreement/proposal operations require actual party membership; an unrelated `superadmin` role alone does not grant private file access, upload, signing or work-transition authority. Existing ordinary administrative engagement visibility remains separately available. Agreement drafts are visible only to the uploading party; district membership is the district party. Shared agreement versions remain accessible to both parties after completion/cancellation/archive. An unrelated district must be denied the proposal-specific route even if that district can separately view the educator's explicitly directory-visible resume.

## Agreement operations

All mutating operations require a stable `requestId`. Reusing it with different arguments fails. Retries return the original result before stale-revision checks, after access checks. `expectedRevision` is the agreement's current revision; stale writes fail with a refresh/retry message. Version numbers are monotonically increasing within one contract. Filename equality never groups agreements.

- `api.agreementVersions.createDraft({ engagementId, title, notes?, privateFileId, requestId })` → `{ contractId, versionId, revision: 1 }`. Creates a distinct identity and private original. No recipient event or notification.
- `api.agreementVersions.attachFirstVersion({ contractId, privateFileId, expectedRevision, requestId })` → `{ contractId, versionId, revision }`. Adds private original version 1 to an existing managed or legacy text-only identity; retains that contract ID/title/notes/history. Only the owning party may attach, and the engagement must be active/in-progress. Requires no existing versions or content pointers; content-bearing legacy records still require guarded migration. Legacy document status is preserved on the new version as `legacyStatus`, not signing evidence. It is receipt-idempotent and stale/duplicate attachment fails. No counterpart event until explicit `share`. Text-only rows have revision zero unless returned otherwise.
- `api.agreementVersions.saveVersion({ contractId, privateFileId, kind: 'revision' | 'signed_copy', parentVersionId, expectedRevision, requestId })` → `{ contractId, versionId, revision }`. Revision requires the parent uploading party and latest parent. Signed copy may be uploaded by either party and requires an explicit shared parent. Saves privately. Existing original/current shared version, signing and work state remain unchanged.
- `api.agreementVersions.share({ contractId, versionId, expectedRevision, requestId })` → `{ contractId, versionId, revision }`. Only uploading party, latest draft. Sharing creates exactly one counterpart in-app/outbox event for that version and selects it as current shared. Repeated sharing cannot duplicate the notification. Deep link: `/dashboard/engagements/<engagementId>?agreement=<contractId>&version=<versionId>`.
- `api.agreementVersions.recordSigning({ contractId, versionId, expectedRevision, requestId, state: 'waiting' | 'signed_externally', note, acknowledged: true })` → `{ revision }`. Requires current shared version. Waiting is uploader-only; external signing may be recorded by either party with explicit note/acknowledgement. Records actor/date/version in activity; does not complete work. A signed-copy upload does not invoke this operation.
- `api.agreementVersions.listForEngagement({ engagementId })` → array of `{ contractId, title, notes?, revision, status, legacy, currentSharedVersionId?, currentVersionState, versions, activity, allowedActions }`. `versions` contains only visible versions: `{ versionId, privateFileId, number, kind, parentVersionId?, fileName, uploadedByUserId, uploaderName, createdAt, sharedAt?, legacyStatus?, coordinationState, downloadUrl, isMine }`, newest first. `activity` contains `{ eventId, action, note?, versionId?, createdAt, actorName }`; private activity is filtered. `currentVersionState` is `none | shared | waiting | signed_externally` for the particular current shared version; each version's `coordinationState` is `draft | shared | waiting | signed_externally`, derived from its own explicit events. A new shared revision starts `shared`; earlier signing evidence stays on the earlier version and in activity. Compatibility `status` is `draft` for private/unsigned shared versions, `sent` for explicit waiting, and `signed_externally` only for the current version's explicit acknowledgement. Legacy status remains historical evidence, not a new signature claim. `allowedActions` contains boolean `attachFirstVersion`, `upload`, `share`, `signedCopy`, `recordSigning`; UI must additionally use version ownership/current-version state to select a specific action. Server checks remain authoritative. `legacy: true` means unmigrated content, with no plaintext fallback.

## Engagement / proposal operations

- `api.engagements.transition({ engagementId, action: 'start' | 'complete' | 'cancel' | 'reopen_need' | 'archive', expectedRevision, requestId, reason?, acknowledged? })` → `{ engagementId, revision, status }`. Existing legacy revision defaults to zero. Start: district manager, active → in_progress. Complete: district manager, in_progress → completed. Cancel: either party, active/in_progress, nonblank reason + acknowledgement that external agreements are not voided. Reopen: district manager, canceled engagement, placed need, no non-canceled hire, reason + explicit acknowledgement; rejected proposals remain rejected. Archive: completed/canceled only, actor's view, retained retrieval. Each meaningful work transition adds activity and counterpart event; archive has no counterpart alert.
- `api.engagements.activity({ engagementId })` → chronological stored engagement event rows with actorUserId/action/note/createdAt. `getById`, `listMine`, `listForNeed` remain; summaries include `revision` (legacy zero) and server-derived `partyAccess`. `partyAccess` is true for the educator, buyer, or a member of the engagement's district and false for unrelated administrative visibility. Clients must use it for private-file queries/actions rather than re-deriving membership from role or user equality. `listMine({ includeArchived?: boolean })` preserves empty-args callers and omits archived items by default. With `includeArchived: true` it returns all, and summaries expose `archivedForViewer` for an Active/Archived filter. `getById` remains retrievable.
- `api.proposals.accept({ proposalId })` retains its arguments and `{ proposalId, engagementId }` result. Repeated acceptance of the same accepted proposal returns the original engagement, including historic canceled acceptance, with no duplicate effects. Concurrent competition remains transactional; one non-canceled hire per need. Reopening permits a replacement proposal while preserving old accepted/canceled history.
- `api.needs.updateStatus` rejects reopening a closed/placed need with engagement history; use the explicit canceled-engagement correction operation.
- `api.messages.send` retains its original interface. If need/engagement context is supplied it must correspond to both conversation parties and an existing proposal/engagement. District initiation/consultant-reply policy remains intact.

## Other file attachment operations and old client compatibility

- `api.educators.setResume({ privateFileId, fileName })` attaches an owned `resume` upload. The registered filename wins. Legacy `storageId` is accepted only as an argument shape to return an explicit upgrade error, never attached.
- `api.credentials.finalizeUpload({ privateFileId?, type, title, issuingBody, state?, issueDate, expiryDate? })` attaches an owned `credential` file; no-file credentials remain supported. Raw `storageId` fails.
- `api.proposals.submit` adds optional `attachmentPrivateFileId`; it must be an owned purpose `proposal` upload registered to that need. Omitting it uses the current private directory resume. Raw `attachmentStorageId` fails. Its existing need/message/rate inputs remain.
- `contracts.generateUploadUrl`, `educators.generateResumeUploadUrl`, `credentials.generateUploadUrl`, `proposals.generateAttachmentUploadUrl`, `users.generateOnboardingResumeUploadUrl` remain exported but return explicit upgrade-required errors after authentication/access checks. `users.completeOnboarding` rejects raw `resumeStorageId`.
- `contracts.create` supports safe text-only private draft creation; continue that same identity with `agreementVersions.attachFirstVersion`, then `share`; raw files/non-draft status fail. `contracts.updateStatus` and `engagements.setStatus` remain exported and reject unsafe ambiguous status actions with an upgrade message. Use the explicit operations above.
- Legacy `getFileUrl`, `getResumeUrl`, `getCredentialFileUrl`, `getAttachmentUrl` return authenticated application routes for migrated/private files, or null when content still requires migration. No ordinary read deletes or converts legacy files.

Replace raw-ID presence checks with new private-file fields.

Fresh onboarding has no user row until profile creation. Retain the selected File locally, complete normal Clerk-backed onboarding, then request/upload/setResume. Suppress onboarding's automatic `viewer.onboarded` redirect until this attachment step completes; preserve File on failure and offer retry or explicitly continue to the profile. Never insert a pre-auth user/role bypass. Returning onboarded educators may use the normal upload sequence.

## Outbox and delivery

Messages, matching-need alerts, submitted/accepted proposals, agreement sharing/signing and work transitions create source-linked notification/outbox rows transactionally. Event + recipient key de-duplicates user events. Need email opt-out suppresses email while retaining in-app notification. States are queued, sending, captured (staging), provider_accepted, failed, invalidated (source removed), suppressed (preference). No delivered claim exists without callback evidence. Recipient, rendered provider payload and origin are frozen on the first claim. Uncertain retries stop 23 hours after the first attempt and require manual reconciliation beyond that window. Three automatic attempts maximum; durable 60-second claim lease plus watchdog recovers interrupted actions; exponential retry uses the same `k12gig:<outboxId>` provider idempotency key. Staging captures rendered text/HTML without calling a provider.

`api.delivery.listForEngagement({ engagementId })` returns authorized party-visible job summaries `{outboxId,eventKey,state,title,attempts,lastError?,createdAt,updatedAt,history,canRetry}` for that engagement, its proposal and agreements. `canRetry` is server-derived and true only for the recipient of a failed job while the three-attempt and 23-hour uncertainty bounds remain open. `api.delivery.listMine({})` returns the latest 200 recipient-owned jobs with `history`, `canRetry`, applying the limit after its indexed recipient filter. Other users' traffic cannot truncate this history. `api.delivery.retry({ outboxId })` remains the authoritative recipient-only mutation. Internal `claim`, `finish`, `dispatch` implement fencing; UI must not invoke them. Provider acceptance is not delivery proof.

## Guarded migration and rollback

Controller only: `internal.privateMigration.migrateLegacy({ dryRun: true })` scans bounded staging sources, verifies content and reports `rows[{sourceId, legacyStorageId, state, sha256?, error?}]`, `migrated`, `retired`, `checkpoints`. Apply requires `{ dryRun:false, confirmation:'ENCRYPT_VERIFIED_STAGING_ORIGINALS', retireOriginals?: true }`. Every source is independent, even identical filenames/storage bytes. Missing/invalid content or ambiguous ownership is blocked. Legacy credential strings are normalized as storage IDs; URL/ambiguous strings require manual review. Absent original filename gets an explicitly generated `legacy-<purpose>.<ext>` filename, never an inferred relationship.

Apply reads exact bytes, encrypts, stores, decrypts the stored copy, verifies size/hash, then transactionally attaches only if the original source snapshot still matches. Existing contract IDs/status/timestamps/events survive; one original version records original status/storage provenance. Legacy completed means legacy document state, not a new signing/work claim. `privateMigration` rows are restartable per-source checkpoints; repeated application is idempotent. Retirement is separately requested and re-verifies stored ciphertext, hash and remaining live references; unresolved/shared originals remain. Application code rollback must retain private-aware download readers; do not revert private files to public plaintext. Data rollback requires restoring source metadata to verified encrypted copies from the private snapshot/checkpoints, never making original bearer URLs public again. Scan bounds fail closed at 500 rows per source table rather than silently omitting records.

Normal `internal.qa.seed` now validates and encrypts synthetic files before storage, then creates owned private files and fixture versions in the seed transaction. It does not create plaintext objects or require a follow-up migration. Its internal `seedRows` helper requires encrypted receipts. Reset tracks derived private/version/checkpoint records, cancels source-linked work, and preserves accounts/memberships and unrelated records; reviewer-created dependent work still blocks reset. Existing pre-release fixtures require the explicit guarded migration once.

Notification destinations: matched need → `/dashboard/board/<needId>/propose` (the existing educator need-detail/proposal route; `/dashboard/board/<needId>` does not exist); new message → `/dashboard/messages?to=<senderUserId>` (existing conversation selector); new proposal → `/dashboard/district/needs/<needId>`; acceptance → `/dashboard/engagements/<engagementId>`; agreement events preserve agreement/version query parameters as above. UI auth/onboarding work must preserve the complete safe relative target.

## Task 3 discovery and account continuity

- `users.claimSeededDemoAccount` remains exported as an authenticated no-op. It never adopts an email-matching seed row. Already-linked records and legacy provenance are unchanged. The frontend no longer mounts the automatic linker. Clerk user/session changes remount the client query cache and application state; old posting/onboarding continuations cannot redirect or attach a file after unmount.
- Directory URL state uses repeatable `area`, `specialization` (`spec` remains accepted), `grade`, `region` (`location` remains accepted), and legacy `engagement`. `availability=accepting` includes open and limited; `reviewed=1`, `saved=1`, and `sort=relevance|availability|rate` round-trip through the shared parser. Profiles carry a validated `returnTo=/browse?...`; auth and role selection retain the entire safe relative destination.
- Browser saved consultants are keyed by actual Convex user ID. Onboarding session fields are keyed by actual Clerk ID. Posting session fields are keyed by actual Convex user ID and draft ID; anonymous previews are a separate browser-session record. Anonymous import requires an explicit action and never preloads an account form. The unattributed legacy localStorage keys are left untouched and are not silently migrated. - `needs.saveDraft` and `needs.create` accept additional optional strings `location`, `deliveryMode`, `compensationBasis`, and `selectedEducatorId`; schema and normalizers preserve them. New posting drafts use delivery values `onsite|remote|hybrid|discuss` and compensation basis `hour|day|project|discuss`. The selected consultant is context only; publishing still uses the existing matching-need alert behavior, without implying a targeted invitation or hire. `educators.getSelectedForPosting({educatorId:string})` requires district authorization and returns `{educatorId,name}` from the actual record, or null. - `admin.recordCredentialReview({credentialId, reviewed:boolean, note, evidenceReference})` requires an authenticated superadmin, an existing credential and nonempty supporting note/reference. It appends an immutable `credentialReviewRecords` row with educator, reviewer and timestamp plus an `adminAuditEvents` event. `reviewed:false` appends a withdrawal. The latest record for a credential determines its reviewed state; historical `credential.verified`, profile tier, QA audit fixtures and background-check IDs are not supporting evidence.
- `credentials.listMine` and `credentials.listForEducatorProfile` add `reviewed:boolean` while preserving original `verified`. Browse response adds `subCategories` and derives its displayed `verificationTier`/credentials badge from explicit review records. Profile completeness remains a separate label; no unsupported background badge is shown. Review note/reference are not exposed to directory viewers. QA reset refuses to orphan untracked review evidence referencing tracked fixtures.
- This task does not add a credential-review administration screen or extend private-file access. The review API records evidence an authorized administrator actually reviewed through an existing authorized source (for example an issuing registry); no automatic registry or background check occurs. The controller's live review gate must establish the evidence and reviewer authority before recording it. An unrelated superadmin still cannot retrieve private agreement/proposal files. Additional private credential-review UI/access needs a separate explicit design if required.

Product facts still unestablished: a nationwide delivery/service policy, a specific retention period, a support SLA, background-check launch availability, and any hiring-time guarantee. Omitted values retain old-client creation behavior; returning onboarded profiles continue through the existing locked-role path. No legacy profile taxonomy values are migrated or collapsed.

## Task 4 release operations

`internal.qa.environment({})` adds `buildCommit` (compiled source literal, local fallback `unbuilt`) and `convexDeployment` resolved from the actual built-in cloud URL. The two exact targets are in `scripts/staging/resources.json` and `automation-resources.json`; mixed target URLs, issuer/instance, capture settings and concrete deployment IDs fail. Stable remains the CLI default; `--automation` loads only its dedicated private environment and deploy overrides without changing stable linkage.

`internal.qa.seed` and `seedRows` add `expectedCommit?:string` to the validated argument shape, but reject missing, non-full-SHA or mismatched values before any seed/no-op. `internal.qa.reset` likewise requires matching compiled revision in addition to its existing confirmation. This applies equally to stable and automation and does not require a new backend before deployment itself. Operator CLI requires `--expected-commit=<full reviewed SHA>` and prohibits stable reset automation.

Both seed APIs and status/reset support the explicit `release-candidate-v1` namespace in addition to unchanged `human-review-v1`. Supplementary seed requires the actual allowlisted base roster, existing ordinary buyer/educator/district membership and distinct encrypted storage receipts not owned by another manifest. It creates only supplementary need/proposal/engagement/agreement/file/version/event records; no credential-review evidence. Existing run returns a no-op. Action-level concurrent retries clean up only their unused uploaded objects. Reset refuses untracked dependents, including immutable credential-review records, and preserves base accounts/manifests.

Automation only: `internal.qa.deliveryFixtures({namespace:'release-candidate-v1',expectedCommit,confirmation:'SIMULATE_CAPTURE_ONLY_DELIVERY'})` returns `{failedId,queuedId}` for idempotent source-linked outbox examples against a tracked supplementary contract. The failed attempt explicitly says SIMULATED; no provider request happened. Use the existing authenticated recipient `api.delivery.retry` and internal delivery claim/dispatch to prove real capture/retry/reset behavior. Reset tracks these source-linked jobs, notifications, attempts and watchdogs. There is no public fixture/auth/role bypass.

Legacy `contracts.listForEngagement`, `contracts.listMine`, `contracts.listEvents` and modern `agreementVersions.listForEngagement` apply one consistent draft visibility predicate even when `managed` is absent. Unmigrated text-only/content-bearing draft metadata and history remain owner/district-team only; legitimate legacy non-draft records remain visible to the two parties. This does not infer sharing from filename or fabricate a version relationship.

### Legacy rehearsal amendment

Automation-only `internal.qa.seedLegacyRehearsal({namespace:'legacy-migration-rehearsal-v1',expectedCommit,confirmation:'CREATE_SYNTHETIC_LEGACY_REHEARSAL'})` returns `{seeded,count}`. It stores only the source-controlled visibly marked synthetic PDF; it accepts no upload/import or identity arguments. Actual QA actors/membership come from the verified base manifest. It produces three content sources sharing one plaintext object plus an independent text-only draft, in ten manifest records. Private migration extends this exact manifest with derived encrypted storage/private files/versions/checkpoints. `qa.status` and guarded `qa.reset` accept this namespace only on automation. Ordinary `qa.seed`/seedRows do not accept this namespace and remain encryption-first. Internal `legacyRehearsalState` and `seedLegacyRehearsalRows` are preflight/finalization helpers with the same exact resource/commit/confirmation gate; the latter additionally checks the fixed source PDF's digest/size before attachment.

Journey receipts now include `commit`. The command passes the commit already verified against `qa.environment` into `runJourney({resources,verifiedCommit,...})`; direct helper callers must provide that verified full SHA. Receipt schema still contains only safe target/commit/case status/timing data and sanitized errors.
